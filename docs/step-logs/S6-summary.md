## S6-T01：通知规则配置

### 实现目的

在订单生命周期的 5 个关键节点自动触发通知，告知客户或摄影师进展。

### 如何实现

文件：`backend/app/services/notification_service.py`

5 个通知模板：
1. `booking_confirmed` - 预约已确认
2. `shoot_reminder` - 拍摄提醒
3. `selection_published` - 选片通知
4. `retouch_feedback` - 修图反馈
5. `delivery_complete` - 交付完成

触发点：
- `selections.py` 创建选片集后触发 `selection_published`
- `retouch.py` 客户提交反馈后触发 `retouch_feedback`
- `deliveries.py` 上传成片后触发 `delivery_complete`

### 改进之处

- `send_notification` 函数永不抛异常，所有错误被捕获并记录
- 通知与业务逻辑完全解耦
- 使用现有 Notifier 抽象层（Bark/企业微信）

### 存在的问题

- `booking_confirmed` 和 `shoot_reminder` 尚未接入触发点
- 无通知模板自定义功能
- 无通知偏好设置（用户无法选择接收渠道）

## S6-T02：通知与状态解耦验证

### 实现目的

确保通知服务失败时，订单状态仍能正确流转。

### 如何实现

- `send_notification` 内部 try/except 捕获所有异常
- 测试中 mock 通知器抛异常，验证状态流转不受影响
- 两个解耦测试：选片发布 + 交付上传

### 改进之处

- 设计层面保证解耦，而非依赖测试约束
- 通知失败仅记录日志，不影响业务流程

### 存在的问题

- 通知失败无重试队列
- 无通知失败告警机制

## S6-T03：最终成片上传

### 实现目的

摄影师上传最终成片（JPEG/PNG/ZIP），订单状态转为 DELIVERED。

### 如何实现

- 路由：`POST /api/v1/orders/{order_id}/delivery`，仅摄影师
- 校验：订单必须为 WAITING_DELIVERY 状态，文件格式和大小
- 存储：使用 Storage 抽象层
- 状态流转：WAITING_DELIVERY -> DELIVERED
- 触发 `delivery_complete` 通知

### 改进之处

- 支持 100MB 大文件（ZIP 打包）
- 上传后自动通知客户

### 存在的问题

- 无分片上传
- 无断点续传
- 无成片预览

## S6-T04：客户下载

### 实现目的

客户下载最终成片，非授权用户返回 403。

### 如何实现

- 路由：`GET /api/v1/deliveries/{id}/download`
- 鉴权：客户只能下载自己订单的成片，摄影师只能下载自己拍摄的
- 返回 FileResponse

### 改进之处

- 严格的权限校验，非参与者无法下载
- 使用 FileResponse 流式传输

### 存在的问题

- 无下载次数限制
- 无下载链接过期机制
- 无防盗链

## S6-T05：订单归档

### 实现目的

摄影师将已交付订单归档，归档后订单只读。

### 如何实现

- 路由：`PATCH /api/v1/orders/{order_id}/archive`，仅摄影师
- 校验：订单必须为 DELIVERED 状态
- 状态流转：DELIVERED -> ARCHIVED

### 改进之处

- 归档是终态，防止误操作
- 归档后订单数据保留，仅状态变更

### 存在的问题

- 归档后未限制修改操作（需在各个 API 加状态检查）
- 无自动归档（如交付后 30 天自动归档）

## S6-T06：前端交付页

### 实现目的

提供交付管理界面，摄影师上传成片和归档，客户查看和下载成片。

### 如何实现

- 页面：`/orders/:id/delivery`
- 摄影师：上传成片（WAITING_DELIVERY）、归档（DELIVERED）
- 客户：查看成片信息、下载成片
- 根据角色和状态显示不同操作

### 改进之处

- 单页面适配两种角色
- 状态驱动的 UI，仅显示当前可用操作
- 下载链接直接指向 API 端点

### 存在的问题

- 无下载进度显示
- 无成片预览
- 归档无确认弹窗
